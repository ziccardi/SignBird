# SignBird Key & Certificate Service

The service manages RSA-2048, ECDSA P-256, and ECDSA P-521 keys, X.509 certificates, and signing credentials for local development. It uses PostgreSQL with `pgx` and queries generated by `sqlc`.

PostgreSQL maps the OIDC pair `(iss, sub)` to an internal user. Each key row links its owner to a `keyId`, the `pkcs12-test` backend, and an `object_ref`. The reference identifies the encrypted container in the `bytea` column `pkcs12_objects.container`. The service decodes the container in memory when it needs the private key for a CSR. PostgreSQL backups include the containers. Keep the container password outside the database.

The entry point is in `cmd/key-certificate-service`. Service logic is in `internal/keycert`. The schema, SQL queries, and code generated by `sqlc` are in `internal/db`.

## Local startup

You need Go 1.24 or later, a dedicated PostgreSQL database, OpenSSL, and a reachable Keycloak realm. Configure Keycloak JWT access tokens to include the API audience. Use the same OIDC settings and internal token for both Go processes.

From the `key-certificate-service` directory, run the following commands.

```sh
export SIGNBIRD_DATABASE_URL='postgres://signbird:password@127.0.0.1:5432/signbird?sslmode=disable'
export SIGNBIRD_OIDC_ISSUER='http://localhost:8180/realms/signbird'
export SIGNBIRD_OIDC_AUDIENCE='signbird-api'
export SIGNBIRD_INTERNAL_TOKEN="$(openssl rand -hex 32)"
export SIGNBIRD_PKCS12_PASSWORD='replace-with-a-test-password'

mkdir -p data
(umask 077; openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -subj '/CN=SignBird Development CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign' \
  -keyout data/ca.key -out data/ca.pem)

export SIGNBIRD_TEST_CA_CERT="$PWD/data/ca.pem"
export SIGNBIRD_TEST_CA_KEY="$PWD/data/ca.key"
make migrate
make run
```

Generate the CA once per environment. Keep the container password, CA, and PostgreSQL data across restarts. Then start the [API Service](../api-service/README.md) with the same issuer, audience, and internal token. The internal service listens on `127.0.0.1:8081` and requires both the API Service token and the user's access token.

For key creation, certificate issuance, and renewal, run the [Signature Activation Service](../signature-activation-service/README.md) and set `SIGNBIRD_ACTIVATION_SIGNER_TOKEN` to the same value in both services. The caller sends a fresh `X-TOTP-Code` for each change, including alias updates.

## Operations

- `GET /v1/keys/capabilities` lists key algorithms, signature schemes, and supported hash algorithms for the test keystore.
- `POST /v1/keys` accepts an optional `algorithm` and defaults to `RSA-2048`. It registers the key and its PKCS#12 container in a single transaction. A retry with the same `Idempotency-Key` returns the same key after the transaction commits.
- `GET /v1/keys` and `GET /v1/keys/{keyId}` return the owner's active keys. The key detail includes certificate history.
- `POST /v1/certificates` generates and verifies a CSR, issues a certificate through the local CA, and registers a signing credential. To renew, repeat the request for the same key with a new `Idempotency-Key`. The certificate history retains previous issuances.

- Key creation and certificate issuance accept an optional `alias`. Use `PATCH /v1/keys/{keyId}` or `PATCH /v1/keys/{keyId}/certificates/{certificateId}` with `{"alias":"New name"}` to rename an existing item. An empty alias clears the display name. Aliases are at most 80 characters and leave key, certificate, and credential identifiers unchanged.

- `POST /v1/keys/{keyId}/csr` creates a signed PKCS#10 request in PEM format for the supplied common name. `POST /v1/keys/{keyId}/certificates` imports a CA-issued PEM certificate and an optional issuer chain. Both require a fresh `X-TOTP-Code`. The import checks the public key, current validity, signing key usage, and the signature links in any supplied chain. Trust in the issuing CA is evaluated by the document recipient. The service registers the imported certificate and a signing credential without changing the key.

Files created by the earlier API Service prototype require an explicit import into the new registry. Key destruction, revocation, and qualified provider integration still need implementation and their respective authorization flows.

## Upgrading from filesystem storage

Stop the old Key & Certificate Service. Run `make migrate` with `SIGNBIRD_KEYSTORE_DIR` set to the previous directory and `SIGNBIRD_PKCS12_PASSWORD` set to the existing password. The migration copies registered containers and checks that active keys match the public keys in PostgreSQL. If a file for an active key is missing or a container cannot be read, the migration rolls back the transaction. The original files remain on disk. After migration, the service reads containers from PostgreSQL and can start without `SIGNBIRD_KEYSTORE_DIR`.

## Verification

```sh
make generate
make test
SIGNBIRD_TEST_DATABASE_URL="$SIGNBIRD_DATABASE_URL" make test-integration
```

The integration test creates and removes a dedicated schema in the specified database.
